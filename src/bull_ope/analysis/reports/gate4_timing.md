## 記録の仕組みとずれの考え方
記録は `blade_state` が届くたび（シミュレーション時刻で 20 ms ごと）に1行を書き、ほかのトピックはその時点の最新値を使う。
`blade_state` の値（力・刃先・地面）は同じステップの値なので、ずれはない。ここでは、ほかの値が `blade_state` に対してどれだけ遅れているかを測る。

| 測り方 | 内容 |
| --- | --- |
| T1 | `sim_time` − `pose_stamp`（`global_pose` の位置が何 ms 前の値か） |
| T2 | `global_pose`・`joint_states` の値が変わる間隔 |
| T3 | 速度の指令が変わってから、`v_forward` が変化量の 10%・63%・90% に達するまでの時間 |
| T4 | 排土板の速度指令 `cmd_lift` と、刃先の上下の速度（`edge_z` の微分）の相互相関が最大になる遅れ |
| T5 | 同じ物理量を別のトピックで見たときの、相互相関が最大になる遅れ |

点検の道具：`analysis/checks/check_timing.py`

## 分かったこと
### 1. 各値の `blade_state` に対する遅れ
| 値 | 遅れ | 根拠 |
| --- | --- | --- |
| `blade_state` の値（力、刃先、地面の高さ） | 0 ms（基準） | 同じステップの値 |
| `joint_states` の値（関節の位置・速度・力、履帯） | 20 ms（1 行） | T5：F_total_z → lift_joint_effort が毎回 20 ms |
| `global_pose` の位置・姿勢 | ふつう 20 ms（1 行）、まれに 60〜100 ms | T1 |
| 計算した速度（`vx`、`vy`、`wz`、`v_forward`、`v_lateral`、`speed`） | 約 60 ms（3 行） | T5：履帯の回転速度（20 ms 遅れ）より、さらに 40 ms 遅れる。位置の変化を 0.1 秒（`VEL_WINDOW`）の幅で求めていることによる遅れと、`global_pose` の遅れを合わせたもの |

`global_pose` と `joint_states` の遅れはいつも同じで、ばらつかない（関門3のデータ 12 件、ex_stop_and_go 3 件とも、中央値・T5 がまったく同じ）。

### 2. 指令から応答までの遅れ
| 指令 | 応答 | 遅れ |
| --- | --- | --- |
| 排土板の速度指令 `cmd_lift` | 刃先が上下に動き始める | 60 ms（3 ステップ）。指令が ROS から Unity に届くまでの時間と、関節の応答を含む |
| 速度の指令 `cmd_vx` | `v_forward` が変化量の 63% に達する | 120〜140 ms。ただし `v_forward` 自体に約 60 ms の遅れがあるので、車体の実際の応答は 60〜80 ms 程度 |
| 速度の指令 `cmd_vx` | `v_forward` が変化量の 90% に達する | 140〜240 ms |


## 決めたこと
| 決めること | 結論 | 理由 |
| --- | --- | --- |
| 値をずらしてそろえるか | **ずらさない** | 遅れは最大でも 3 行（60 ms）で、毎回同じ。推定器の時間窓（下の 1.2 秒以上）に比べて十分短い。ずらすと、まれな遅れ（最大 100 ms）の行で逆にずれる |
| 計算した速度の遅れ | 記録の仕組みは変えず、遅れ（約 60 ms）をドキュメントに残す | `VEL_WINDOW` を短くすると遅れは減るが、速度の揺れが大きくなる。速度は一定で走るエピソードでは大きく変わらない |
| 指令が変わった直後の扱い | 速度の指令が変わってから約 0.3 秒（90% の最大 240 ms）は、応答の途中として扱う。学習に使う区間の決め方は、深さの追従の落ち着き（関門3：1.5 秒）と合わせて段階8で決める | — |
| 時間窓の長さの下限 | **1.2 秒以上**（地形のマスによる約 0.6 秒の変動を2周期以上含む）。最終的な長さは段階8で決める | 遅れや応答時間（最大 240 ms）はこれより十分短い |
